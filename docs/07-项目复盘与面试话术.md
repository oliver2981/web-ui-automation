# 07 项目复盘与面试话术

> 这是最后一篇,把整个项目**怎么讲给面试官听**串起来。看完之后,你应该能:用 STAR 把这个项目讲清楚、答上高频追问、说出电梯陈述。

---

## 一、电梯陈述(30 秒版本)

面试一开场,如果被问"介绍一下你的自动化项目",用这一段:

> "我独立搭了一套基于 **Playwright** 的 UI 自动化测试框架,用 Python 写的,对 saucedemo 电商网站做了**端到端测试**,覆盖**登录、商品、购物车、结算**四个模块。整体用了 **Page Object 模式**做分层——页面元素和操作封装在 `pages/`,测试用例只写业务和断言,这样网站改版时只改一处。用例层用 **pytest** 组织,登录模块覆盖了正常、锁定、密码错误三类场景(其中锁定和密码错误两类用 **参数化** 组织),还集成了 **Allure 报告**,用例失败会**自动截图**附加到报告里。现在 9 条用例全部通过。"

这段话里塞进了几个**关键词**——Playwright、Page Object、pytest、参数化、Allure、失败截图。面试官往往会顺着这些词往下问,所以下面的追问要熟。

---

## 二、用 STAR 讲这个项目

**STAR** 是回答行为类问题的框架:S(情境)→ T(任务)→ A(行动)→ R(结果)。

### S —— 情境(Situation)

我为了系统地练习 UI 自动化测试,想找一个**有完整业务流程**的真实网站来练手,而不是只测一个孤立的页面。saucedemo.com 是专门给测试练习用的电商站,正好有"登录 → 挑商品 → 加购物车 → 结算 → 下单成功"这条完整链路,而且元素上带了 `data-test` 属性,适合练习稳定的定位。

### T —— 任务(Task)

我要搭一个**结构清晰、可维护、能出报告**的自动化测试框架,而不是把一堆点击操作堆在一个文件里。具体要求:
- 能覆盖主流程(登录、商品、购物车、结算)各个模块;
- 代码要分层,页面改动时不用大改用例;
- 要能覆盖多组测试数据(如不同账号的登录结果);
- 跑完要有一份**能说明问题**的报告,失败时便于定位。

### A —— 行动(Action)

- **技术选型**:选 Playwright + pytest。Playwright 内置自动等待,不用手写 sleep,写起来稳;用官方 `pytest-playwright` 插件,`page` 自动注入,省去启动/关闭浏览器的样板代码。
- **分层设计**:抽了一个 `BasePage` 基类,把点击、输入、取文本这些通用操作放进去;`LoginPage`、`ProductsPage`、`CartPage`、`CheckoutPage` 都继承它,只写自己页面独有的元素和动作。这样**定位集中一处,改一处到处生效**。
- **消除重复**:在 `conftest.py` 里写了 `logged_in` fixture,把"打开网站 + 登录"抽出来,商品、购物车、结算用例直接用它,不用重复写登录。
- **数据与逻辑分离**:把账号数据放进 `data/users.json`,用 `@pytest.mark.parametrize` 让一个登录失败用例跑两组数据(锁定用户、密码错误),扩展时只加数据不改代码。
- **报告与排错**:用 `--alluredir` 产出 Allure 结果,并在 `conftest.py` 里用 `pytest_runtest_makereport` 钩子实现"用例失败时自动截图并附加到报告"。

### R —— 结果(Result)

- 覆盖了**登录、商品、购物车、结算**四个模块,共 **9 条用例,全部通过**。
- 代码分层清晰:页面改动只需改 `pages/`,用例层稳定。
- 登录模块覆盖了**正常登录、锁定用户、密码错误**三种情况,其中锁定用户和密码错误两类由 `@pytest.mark.parametrize` 参数化驱动。
- 集成 Allure 报告 + 失败自动截图,失败时能**直接看到当时的页面**,定位问题的效率明显提高。
- 我自己对 **Page Object、fixture、参数化、钩子**这些自动化测试的核心概念,从"听说过"变成了"能讲清、能写出来"。

> **诚实提示**:这是个人练习性质的测试项目(测的是公开练习网站),不是公司生产项目。面试时如实说"这是我为了练习自动化测试自己搭的项目"即可,不用包装成公司业务。真实的定位反而加分——它说明你**主动动手**。

## 三、高频追问与参考回答

### Q1:为什么用 Page Object 模式?

> "因为如果直接在用例里写元素操作,**同一个选择器会在很多用例里重复出现**。网站一改版,每个用例都得改,漏一个就挂。Page Object 把每个页面封装成一个类:元素定位和操作放在类里,用例只调方法、只写断言。好处有三:一是**改一处到处生效**——选择器只在一个文件里;二是**用例干净可读**,像 `products.add_backpack_to_cart()` 这样一眼看懂业务;三是**操作可复用**,比如登录动作所有用例都能用。本项目还抽了个 `BasePage` 放通用操作,子类继承它,避免重复。"

### Q2:参数化是怎么做的?

> "用 pytest 的 `@pytest.mark.parametrize` 装饰器。比如登录失败用例,我在装饰器里列出两行参数——`('locked', 'locked out')` 和 `('wrong_password', 'do not match')`,声明了两列 `case_key` 和 `expected_word`。pytest 会**按每行数据各跑一遍**,一个函数就变成两条独立用例,报告里也分开显示。账号数据我放在 `data/users.json` 里,用 `case_key` 去取,做到**数据和逻辑分离**。以后要加一种失败场景,只加一行数据和一组账号,**函数体不用动**。这就是参数化的价值。"

### Q3:脚本失败了怎么办?你怎么排查?

> "分几种情况。**如果是我脚本自身的问题**(比如定位写错、断言写错),看报错的行号就直接能定位。**如果是页面真的变了**(比如元素属性改了),那正好说明测试起到了作用;我优先看元素定位是否还有效。本项目还专门做了一件事:**用例失败会自动截图**,通过 `conftest.py` 里的 `pytest_runtest_makereport` 钩子,在测试体失败那一刻截一张带时间戳的图,附到 Allure 报告里。所以我排查时**先打开 Allure 报告看失败截图**,一眼就知道失败时页面停在哪、有没有报错弹窗,比光看 `AssertionError` 高效得多。"

### Q4:Playwright 和 Selenium 怎么选?

> "简单说:**Playwright 最大的优势是内置自动等待**。它在你点击/输入前会自动等元素变成可操作状态,所以基本不用手写 `sleep` 或显式等待——而这恰恰是 Selenium 里最容易出问题、也最常写的地方。此外 Playwright 的 API 更现代、安装完一条 `playwright install` 就把浏览器装好了。Selenium 的优势是**生态老、社区大、老项目多**,很多公司的存量脚本是它写的。所以我的判断是:**新项目、追求稳定省心,我选 Playwright;要维护公司已有的 Selenium 脚本,那就继续用 Selenium。** 本项目我选 Playwright,就是为了少踩等待的坑。"

### Q5(可能追问):`fixture` 是什么?你项目里怎么用的?

> "fixture 是 pytest 里**可复用的'测试前准备'**。把它定义在 `conftest.py` 里,测试函数只要把它的名字写成参数就能用。本项目里我写了 `logged_in`:它打开网站、用标准账号登录、然后把登录好的 `page` 返回。所有需要'已登录'的用例——商品、购物车、结算——直接写 `def test_xxx(logged_in)` 就拿到了登录态,登录步骤一个字都不用重复。而登录本身的用例不能用它,因为要测的就是登录,所以那些用例接收原始的 `page`,自己控制输入。"

### Q6(可能追问):测试通过就代表没问题吗?

> "不代表。UI 自动化只能验证**通过界面能看到的行为**,不能替代接口测试、单元测试;而且它只能测**写出来的场景**,没覆盖的场景测不到。它最大的价值是**回归**——比如网站改版后,一键把主流程跑一遍,快速发现'原来好用的功能有没有被改坏'。所以它是我测试工具箱里的一环,不是全部。"

> **小提醒**:上面的回答里,凡是提到项目里的东西,都能在代码里对上号。面试官如果让你打开代码看,这些都能印证——**别背不存在的功能**。本项目实际有:Playwright + pytest + Page Object + parametrize + Allure + 失败截图。它**没有**多浏览器矩阵、没有 CI、没有 CSV 数据驱动,被问到就说"目前还没做,但我了解它是用来做什么的",诚实反而是加分项。

## 四、把七篇串起来:一张项目全景图

```
需求:自动化测试 saucedemo 的下单主流程

① 环境    Python + venv + pip 装依赖 + playwright install         (第 01 篇)
      │
② 入口    你在命令行敲 pytest                                     (第 01 篇)
      │
③ 配置    pytest.ini 决定去哪找用例、结果写到哪                    (第 04 篇)
      │
④ 准备    conftest.py 的 logged_in fixture 先登录好                (第 04 篇)
      │
⑤ 用例    tests/ 里写业务和断言                                    (第 04 篇)
      │        assert cart.get_item_count() == 1
      │
⑥ 页面    pages/ 里的 Page Object 封装定位和操作                   (第 03 篇)
      │        products.add_backpack_to_cart()
      │
⑦ 驱动    Playwright 操作真浏览器(fill / click / 自动等待)         (第 02 篇)
      │
⑧ 定位    用 [data-test='...'] 找到元素,断言检查结果              (第 05 篇)
      │
⑨ 报告    失败 → 钩子自动截图 → Allure 报告里可见                  (第 06 篇)
```

面试时如果紧张,就顺着这张图从上往下讲,逻辑不会乱。

## 五、小结

- 用 **STAR** 讲项目:S 是选了个有完整流程的练习站;T 是搭一个分层、可维护、能出报告的框架;A 是选型 + Page Object 分层 + fixture 去重 + 参数化 + 钩子截图;R 是 9 条用例全绿、结构清晰、报告可用。
- 高频追问就四个核心:**为什么 Page Object、参数化怎么做、失败怎么排查、Playwright vs Selenium**。每个都能用本项目的真实代码作答。
- 记住电梯陈述里的关键词:Playwright、Page Object、pytest、参数化、Allure、失败截图。
- **诚实**:这是个人练习项目,不带包装;说清"做到了什么"和"还没做什么",比夸大更可信。

到这里,七篇学习笔记就结束了。建议的复习顺序:`01 → 02 → 03 → 05 → 04 → 06 → 07`(先建立整体印象和"怎么操作浏览器",再看框架细节,最后背话术);面试前重点看 `07`。
