# 05 元素定位与断言

> 这篇讲两件事:**怎么在网页上"找到"一个元素**(定位),以及**怎么"检查"结果对不对**(断言)。这是 UI 自动化里最基础、也最容易踩坑的部分。

---

## 一、为什么要"定位"?

自动化操作一个网页,第一步永远是:**找到那个元素**。你想点"登录"按钮,得先让代码知道"哪个按钮才是登录按钮"。这个"告诉代码元素在哪"的过程,就叫**定位(locate)**。

在 Playwright 里,定位就是给 `page.locator("...")` 传一个**选择器字符串**。

---

## 二、常见的定位方式

| 方式 | 写法举例 | 说明 |
|---|---|---|
| ID | `#login-button` | 元素的 `id` 属性,唯一,很稳 |
| class | `.cart_item` | 元素的 `class` 属性,可能多个元素共用 |
| CSS 属性 | `[data-test='username']` | 按任意属性匹配,最灵活 |
| 文本 | `text=登录` | 按页面上显示的文字找 |
| XPath | `//button[@id='login']` | 按路径找,功能强但可读性差 |

**越靠前的通常越稳定。** 因为 `id` 和专用属性是"故意给测试用的锚点",不会因为样式调整而变;而 class 经常因为改样式被换掉,文本会因为文案改动而失效。

---

## 三、本项目为什么统一用 `[data-test='...']`?

打开任意一个页面类,比如 `pages/login_page.py`:

```python
class LoginPage(BasePage):
    # 元素定位(用站点自带的 data-test 属性,最稳定)
    USERNAME_INPUT = "[data-test='username']"
    PASSWORD_INPUT = "[data-test='password']"
    LOGIN_BUTTON = "[data-test='login-button']"
    ERROR_MESSAGE = "[data-test='error']"
```

`[data-test='username']` 是一条 CSS 属性选择器,意思是:**找 `data-test` 属性等于 `username` 的那个元素**。

**为什么统一用它?** 因为 saucedemo.com 这个练习站在每个关键元素上都加了一个 `data-test` 属性,**专门给自动化测试当"锚点"**。它:

1. **稳定** —— 这个东西就是为测试加的,不会因为改样式、改文案而被删,比 class 和文本可靠得多。
2. **唯一** —— 一个名字对应一个元素,不会一下子选中一堆。
3. **可读** —— 一眼看出这是"用户名输入框"还是"登录按钮"。

所以在给一个陌生网站写自动化时,**优先找有没有类似 `data-test` / `data-testid` 这种测试专用属性**;有就用它;没有才退而求其次用 `id`、CSS 或文本。

> **本项目里的例外**:有两处没有用 `data-test`,见 `pages/cart_page.py`:
>
> ```python
> class CartPage(BasePage):
>     CART_ITEMS = ".cart_item"          # 购物车里的每一行
>     ITEM_NAME = ".inventory_item_name"  # 每行里的商品名
> ```
>
> 因为购物车列表里**并不是每一行都有 `data-test`**,而 `.cart_item`、`.inventory_item_name` 这类 class 是页面结构里稳定的一环,所以这里用了 class 选择器。**原则是"能用最稳的就用最稳的",不是死磕一种方式。**

## 四、一个页面上有多个同类元素怎么办?

有时候一个选择器会匹配到**多个**元素。比如购物车里可能有好几行商品,每行都有一个商品名。这时:

- 想知道**有几个**,用 `.count()`:

  ```python
  def get_item_count(self) -> int:
      """返回购物车里的商品行数。"""
      self._wait_until_loaded()
      return self.page.locator(self.CART_ITEMS).count()
  ```

  `page.locator(".cart_item").count()` 返回匹配到的元素个数(一个数字)。

- 想拿到**所有的文本**,用 `.all_inner_texts()`:

  ```python
  def get_item_names(self) -> list[str]:
      """返回购物车里所有商品的名字。"""
      self._wait_until_loaded()
      return self.page.locator(self.ITEM_NAME).all_inner_texts()
  ```

  `.all_inner_texts()` 返回一个**列表**,比如 `["Sauce Labs Backpack"]`。`-> list[str]` 是类型提示,表示"返回一个字符串列表"。

> 注意 `get_item_count` 和 `get_item_names` 开头都调了一个 `self._wait_until_loaded()`。这是**主动等待**:它调用 `page.locator(self.CHECKOUT_BUTTON).wait_for()`,意思是"等结算按钮出现再往下走"。为什么需要?因为从商品页点进购物车后,购物车页面**正在渲染**,如果立刻去数商品,可能数到 0(页面还没画出来)。等一个"只在购物车页才有的元素"出现,就说明页面加载好了。方法名前面带下划线 `_` 是本项目的约定,表示"这是内部用的辅助方法,外部不用直接调"。

## 五、断言:检查结果对不对

**定位是"去操作",断言是"去检查"。** 用例跑完操作后,要用 `assert` 判断结果是否符合预期。

本项目用到的断言有三种典型:

### 1. 精确相等 —— `==`

最常见。检查某个文本**完全等于**期望值。

`tests/test_products.py`:

```python
def test_products_title_after_login(logged_in):
    """登录后应进入商品页。"""
    assert ProductsPage(logged_in).get_title() == "Products"
```

断言页面标题**正好是** "Products"。

`tests/test_checkout.py` 结尾:

```python
    assert checkout.get_complete_message() == "Thank you for your order!"
```

断言下单成功文案**正好是** "Thank you for your order!"。

### 2. 文本包含 —— `in`

当你不确定完整文案、或者报错信息里裹着一堆内容时,用 `in` 只检查**包含关键词**。这比精确相等更"抗变化"。

`tests/test_login.py`:

```python
    assert expected_word in login.get_error_message().lower()
```

断言"期望的那个词出现在报错信息里"。配合 `.lower()`(转小写),就能做到不区分大小写地匹配。

`tests/test_cart.py`:

```python
    assert "Sauce Labs Backpack" in cart.get_item_names()
```

断言商品名列表里**包含** "Sauce Labs Backpack"。

### 3. 数量判断 —— `== 数字`

检查"有几个"。`tests/test_cart.py`:

```python
    assert cart.get_item_count() == 1
```

断言购物车里**正好有 1 件**商品。`tests/test_products.py` 里对购物车角标也是:

```python
def test_add_backpack_updates_cart_badge(logged_in):
    """把背包加入购物车,购物车角标应显示 1。"""
    products = ProductsPage(logged_in)
    products.add_backpack_to_cart()
    assert products.get_cart_count() == "1"
```

角标文字是字符串,所以和 `"1"`(带引号)比较。

**怎么选断言方式?** 一张小抄:

| 你想确认 | 用 |
|---|---|
| 文本和期望一字不差 | `== "期望值"` |
| 文本里包含关键字(更抗改文案) | `"关键字" in 实际文本` |
| 元素个数 / 数字 | `== 数字`(注意角标文字要写 `"1"`) |
| 元素是否出现/可见 | `is_visible()` 或 `count() > 0` |

> **小提醒**:断言要点是**"测业务结果,不测实现细节"**。比如断言"登录后标题是 Products"(业务结果),比断言"用户名输入框的边框是灰色"(实现细节)更有价值,前者不会因为改样式而误报。

---

## 六、定位与断言在本项目的分工

回顾一下:定位和操作都封装在 `pages/` 里,断言只出现在 `tests/` 里。

- **`pages/*.py`** 只负责"找到元素、操作元素、把结果取出来",比如 `get_title()` 返回标题文字。
- **`tests/*.py`** 拿这些结果去 `assert`。

这么做的好处和 Page Object 一致:**页面细节(定位)集中在 pages,业务判断(断言)集中在 tests**。以后网站改了选择器,只改 pages,断言逻辑不动。

---

## 七、小结

- **定位**:用 `page.locator("选择器")`。"最稳"的优先级大致是:**测试专用属性(`data-test`)> id > CSS/class > 文本**。
- 本项目**统一优先用 `[data-test='...']`**(站点为测试预留的锚点);个别没有该属性的地方退回 class 选择器。
- 一个选择器匹配多个元素时,用 `.count()` 数个数、`.all_inner_texts()` 取全部文本。
- **断言**三种典型:`==`(精确相等)、`in`(文本包含)、`== 数字`(数量)。选哪种就看你到底想确认什么。
