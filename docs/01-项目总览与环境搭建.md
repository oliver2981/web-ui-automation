# 01 项目总览与环境搭建

> 自己的第一篇笔记：先把项目是干嘛的、代码怎么跑起来、目录怎么分、环境怎么搭捋一遍，细节留给后面几篇。

---

## 一、这个项目是做什么的

一句话：**用代码指挥浏览器，自动帮我点页面、填表单、检查结果对不对。**

测的站点是 [saucedemo.com](https://www.saucedemo.com/)——一个专门给测试练手用的假购物网站，下单流程挺完整：

```
打开网站 → 输入账号密码登录 → 挑商品加入购物车 → 进购物车 → 结算 → 填写收货信息 → 下单成功
```

代码就是把这个流程自动走一遍，每一步都**检查页面是不是符合预期**。比如：输入对的密码后，页面标题应该变成 "Products"；加购之后，购物车角标应该变成 "1"。

哪一步和预期对不上，用例就**失败**，并且自动**截图**，方便回头排查。

## 二、跑一次 pytest，代码是怎么走的

这里说的"请求"，其实就是：**在命令行敲下 `pytest` 之后发生了什么。**

```
你敲下 pytest
   │
   ▼
pytest 读取 pytest.ini           ← 决定"去哪找测试、用什么参数"
   │
   ▼
pytest 加载 conftest.py          ← 这里定义了公共的 fixture(测试前的准备工作)
   │
   ▼
pytest 扫描 tests/ 文件夹        ← 找出所有 test_*.py 里 test_ 开头的函数
   │
   ▼
对每个测试函数:
   1. 先准备它需要的 fixture(比如打开浏览器、登录)
   2. 再执行测试函数里的代码
   3. 测试函数调用 pages/ 里的页面对象
   4. 页面对象通过 Playwright 操作真实浏览器
   5. 用 assert 检查结果
   │
   ▼
如果失败 → conftest.py 里的钩子自动截图
   │
   ▼
测试结果写进 allure-results/(给报告用)
```

拿项目里真实的代码对一遍这条链：

- `pytest.ini` 里写着 `testpaths = tests`，告诉 pytest：**只去 `tests/` 找测试**。
- `conftest.py` 里定义了一个叫 `logged_in` 的 fixture，负责"打开网站并登录好"。
- 测试函数（比如 `tests/test_checkout.py` 的 `test_checkout_flow_completes`）拿到已经登录好的页面，开始走业务流程。
- 测试函数不直接碰浏览器，而是 new 出一个个"页面对象"（如 `ProductsPage`），调它们的方法。
- 页面对象内部再调 Playwright，真正去点、去填。

**为什么分成这么多层？** 一句话：让"页面怎么点的细节"和"业务逻辑"分开，改页面时不用动用例。这块 03 里再细记。

## 三、目录结构逐层解释

```
web-ui-automation/
├── config/                 # 全局配置:那些"改一处、到处生效"的常量
│   ├── __init__.py
│   └── settings.py
├── data/                   # 测试数据(账号密码等)
│   └── users.json
├── pages/                  # Page Object:每个页面封装成一个类
│   ├── __init__.py
│   ├── base_page.py        # 所有页面对象的"爸爸"(基类)
│   ├── cart_page.py
│   ├── checkout_page.py
│   ├── login_page.py
│   └── products_page.py
├── tests/                  # 测试用例:真正写"检查什么"的地方
│   ├── __init__.py
│   ├── test_cart.py
│   ├── test_checkout.py
│   ├── test_login.py
│   ├── test_products.py
│   └── test_smoke.py
├── utils/                  # 通用工具
│   ├── __init__.py
│   └── logger.py           # 统一日志封装
├── .gitignore
├── conftest.py             # 公共 fixture + 失败自动截图钩子
├── pytest.ini              # pytest 的配置
├── README.md
└── requirements.txt
```

逐个说：

- **`config/`** —— 放"常量"。比如站点地址、测试账号、超时时间。好处是：网站换域名了，只改这一处，所有代码跟着生效。`config/settings.py` 长这样：

  ```python
  # 项目全局配置:所有"改一处、到处生效"的常量都放这里

  # 被测站点首页
  BASE_URL = "https://www.saucedemo.com/"

  # 站点自带的公开测试账号(密码对所有账号都相同)
  STANDARD_USER = "standard_user"
  STANDARD_PASSWORD = "secret_sauce"

  # 元素等待超时(毫秒)
  DEFAULT_TIMEOUT_MS = 10000
  ```

- **`data/`** —— 存放测试数据，和代码分开放。`data/users.json` 里是几组账号：

  ```json
  {
    "standard": { "username": "standard_user", "password": "secret_sauce" },
    "locked": { "username": "locked_out_user", "password": "secret_sauce" },
    "wrong_password": { "username": "standard_user", "password": "wrong_password" }
  }
  ```

  `standard` 是能正常登录的账号；`locked` 是被锁定、登录会报错的账号；`wrong_password` 是密码错的账号。04 里记它怎么被用起来。

- **`pages/`** —— **Page Object 层**，项目核心。每个网页封装成一个类，类里写着"这个页面上有哪些元素""能对这个页面做什么操作"。用例只要调方法名，不用关心元素怎么写。

- **`tests/`** —— **测试用例层**。这里才是真正"写检查"的地方，比如断言标题等于 "Products"。一个文件对应一个模块（登录、商品、购物车、结算）。

- **`utils/`** —— 放多个地方都要用的小工具。目前只有 `logger.py`（日志）。

- **`conftest.py`** —— pytest 的"特殊约定文件"。名字固定，pytest 会自动加载。里面放公共 fixture 和钩子（钩子 = 在测试某个时机自动执行的函数）。我这里用它做了两件事：提供 `logged_in`（先登录）、失败时自动截图。

- **`pytest.ini`** —— pytest 的配置文件：

  ```ini
  [pytest]
  addopts = -v --alluredir=allure-results
  testpaths = tests
  ```

  - `testpaths = tests`：`pytest` 不带参数时，只去 `tests/` 找用例。
  - `addopts = -v --alluredir=allure-results`：`-v` 是显示详细输出，`--alluredir=allure-results` 是**每次跑测试都把结果写进 `allure-results/` 文件夹**，后面用它生成报告。

- **`requirements.txt`** —— 项目依赖清单。别人拿到这个项目，一条命令就能装齐所有库：

  ```
  playwright>=1.40
  pytest>=8.0
  pytest-playwright>=0.5
  allure-pytest>=2.13
  ```

  `>=` 表示"这个版本或更新的版本都可以"。四个库分别是：Playwright（操纵浏览器）、pytest（测试框架）、pytest-playwright（把两者接起来的插件）、allure-pytest（生成报告）。

- **`.gitignore`** —— 告诉 git 哪些文件不用提交（比如虚拟环境 `.venv/`、缓存 `__pycache__/`、截图和报告这些"跑一次就产生"的东西）。

> **注意**：Windows 路径分隔符和 Linux 不一样。这里的命令以 Windows(bash) 为准，路径用 `/`。

## 四、环境搭建：一步一步来

### 第 0 步：确认装了 Python

打开终端（Windows 上是 PowerShell 或 Git Bash），输入：

```bash
python --version
```

应该看到类似 `Python 3.11.x` 的输出。**如果提示找不到命令**，说明 Python 没装或没加进 PATH，需要先去 python.org 下载安装，安装时记得勾选 "Add Python to PATH"。

### 第 1 步：创建虚拟环境

**虚拟环境是什么？** 可以理解成"给这个项目单独开的一个小房间"，项目要的库都装在这个房间里，不会和电脑上其他项目打架。

```bash
python -m venv .venv
```

这会在当前目录下生成一个 `.venv/` 文件夹（命令里只要写 `.venv`，Python 会自动补全成完整路径）。

### 第 2 步：激活虚拟环境

```bash
source .venv/Scripts/activate
```

激活成功后，命令行前面会出现 `(.venv)` 字样，表示"你现在在这个小房间里"。

> **常见报错**：`No such file or directory`。多半是路径写错。Windows 的激活脚本在 `.venv/Scripts/` 下（不是 Linux 的 `.venv/bin/`）。如果报"禁止运行脚本"之类的权限错误，可以改用命令提示符（CMD）执行 `.venv\Scripts\activate.bat`，或在 PowerShell 里执行 `Set-ExecutionPolicy -Scope Process Bypass` 后再激活。

### 第 3 步：安装依赖

```bash
pip install -r requirements.txt
```

`-r` 表示"按照这个文件里列的清单装"。这一步会联网下载前面说的四个库。

> **常见报错**：`pip 不是内部或外部命令` —— 说明虚拟环境没激活成功，回到第 2 步。或者网络慢导致下载超时，可以换国内镜像源加 `-i https://pypi.tuna.tsinghua.edu.cn/simple`。

### 第 4 步：下载浏览器

Playwright 需要单独下载它控制的浏览器（不是用平时上网的浏览器）：

```bash
playwright install chromium
```

`chromium` 是 Chrome 的开源版本。**这一步一定要做**，否则测试一跑就报"找不到浏览器"。

> **常见报错**：
> - `playwright: command not found` —— 说明第 3 步没装成功，或者虚拟环境没激活。
> - 下载卡住/超时 —— Playwright 的浏览器是从国外服务器下载的，网络不好时可以多试几次，或设置国内镜像（环境变量 `PLAYWRIGHT_DOWNLOAD_HOST`）。

### 第 5 步：跑第一遍测试

```bash
pytest
```

如果一切正常，会看到类似这样的输出：每个用例前面有个绿点或 `PASSED`，最后一行是 `8 passed`。

想**看着浏览器真的动起来**，加 `--headed`：

```bash
pytest --headed
```

`--headed` 意思是"打开有界面的浏览器"（默认是**无头模式 headless**，浏览器在后台悄悄跑，看不见但更快）。

只想跑某一个文件：

```bash
pytest tests/test_login.py
```

## 五、心得

- 环境这块看着步骤多，其实就是四步：建虚拟环境 → 激活 → 装依赖 → 装浏览器，配一次以后就不用再管了。
- 最容易卡的两处：一是虚拟环境没激活就去 `pip install`（会报找不到 pip），二是忘了 `playwright install`（跑起来报找不到浏览器）。这两个坑我都踩过，记一下。
- 我自己最顺手的记法是：**`pages/` 负责"怎么点"，`tests/` 负责"检查什么"**，`config/` 和 `data/` 负责把易变的东西抽出去。记住这条，看目录就不晕了。
